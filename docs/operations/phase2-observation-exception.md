# Phase 2 관측 조건 예외안

후속 실행 설계와 검증은 [Phase 2 관측 기간 예외와 복구 기록](phase2-reviewed-cutover.md)을 참조한다. 아래 내용은 #51 스냅샷 단계 준비 시점의 기록이다.

## 결정 범위와 현재 상태

사용자는 24시간 zero-fallback 관측 조건을 생략하는 예외안 준비에 동의하였다. 원본 보존, 백업·복구 가능성, DB 호환성 검증은 유지한다. 관측 완료를 선언하거나 지표·관측 시각을 수정하여 통과시키지 않는다.

현재 상태는 **DB 스냅샷 단계 구현·로컬 복원 검증 완료, 관측 예외 실행 제어 미구현, 운영 전환 미실행**이다. 기존 CD에 스냅샷 전용 단계를 추가한다. 기존 배포 단계·SQL·운영 설정은 유지한다. 데이터 손실이 없다는 운영 검증 결과는 아직 없다.

## DB 스냅샷 선행 작업

사용자는 수동 재가져오기 없이 복구할 수 있도록 DB 정보를 먼저 보존한 뒤 진행하도록 요청하였다. 여기서 이전 원본은 Garage의 이전 객체 경로를 의미하며 NAS의 별도 보관 파일과 구분한다. 동일 내용의 새 객체와 연결 정보가 검증되면 이전 객체 전부의 영구 보존은 필수 조건이 아니다.

기존 `Authorized API Schema Cutover` workflow의 `snapshot` 단계는 master·production 환경·기존 동시 실행 잠금을 유지한다. 배포 이미지와 관측 입력을 거부하며 cutover 작업과 상호 배타적으로 실행한다. 서비스 중지, migration, Garage 삭제, web 게시는 수행하지 않는다.

`server/release-db-snapshot.sh`는 전체 DB custom-format dump에 프로젝트·파일 참조·이관 기록·DB 이력을 함께 저장한다. 서버 내부의 제한된 백업 디렉터리에 dump와 checksum을 보존하고 외부 네트워크·운영 볼륨이 없는 임시 PostgreSQL에서 복원을 검사한다. DB 내용은 GitHub artifact나 로그로 업로드하지 않는다.

온라인 dump는 PostgreSQL 내부의 일관된 시점 복사본이다. 이후 발생한 쓰기나 Garage 객체 변경까지 동결하지 않으므로 최종 contract 직전 쓰기 중지 상태의 백업을 대체하지 않는다. DB dump에는 파일 내용이 없으며, 기존·새 Garage 객체가 모두 삭제되면 DB만으로 파일을 복원할 수 없다. 따라서 파일 복사본·checksum·연결 정보 검증 전에는 contract나 원본 삭제를 실행하지 않는다.

로컬 검증은 PostgreSQL 16의 격리 fixture에서 수행하였다. 프로젝트·자산·원본/새 경로 대응·migration·관측 지표 5개 테이블의 복원, dump checksum, 파일 권한 `600`, 성공 후 백업 보존, 시험 컨테이너 정리를 확인하였다. 운영 DB의 복원 검증 결과와는 구분한다.

복원 시험은 메모리 1 GiB·tmpfs 768 MiB로 제한한다. 운영 DB가 제한을 초과하면 검증 실패로 종료하고 이미 검증된 dump와 비공개 오류 기록을 보존한다. 해당 실패는 운영 복원이 아니라 시험 환경 용량 부족일 수 있으므로 결과를 구분하여 처리한다.

## 기존 절차의 제약

1. `.github/workflows/release-api-cutover.yml`은 authorize와 서버 전환 단계에서 관측 확인을 요구한다. `server/deploy.sh`도 서버 관측 기록의 24시간 경과를 검사한다.
2. `apps/api/src/modules/migration/contract-preflight.ts`의 `legacyBridgeObservations` 검사와 `20260822000000_canonical_asset_contract/migration.sql`의 DB 검사가 별도로 존재한다. SQL은 실제 업무 데이터가 있으면 누락·비영(非零) 지표와 24시간 미경과를 거부한다. CD 입력 변경만으로 예외를 적용할 수 없다.
3. contract SQL은 `canonical_object_relocations`의 원본을 `orphan_objects`에 즉시 처리 가능한 `PENDING`으로 등록한다. 기존 취소 상태도 갱신하므로, 전환 전에 취소 표시만 설정하는 방식은 원본 보존 대책으로 불충분하다. 기존 correction 보호용 PREPARED upload intent를 유지하면 contract의 활성 참조 검사에서 거부되므로 이를 그대로 재사용할 수도 없다.
4. `deploy.sh backup`은 쓰기 중지 후 PostgreSQL dump와 SHA-256을 생성한다. 복원 시험은 수행하지 않는다. Garage inventory는 파일 목록이며 파일 내용의 백업이 아니다.
5. contract 이후에는 이전 Phase 1 이미지로 자동 복귀할 수 없다. 기존 절차도 전진 복구 또는 별도로 승인한 DB 복원·Garage 대조를 요구한다.

| 영역 | 필요한 변경과 유지 조건 |

| DB 전환 | 기존 SQL에는 예외 인터페이스가 없다. 역사적 SQL·checksum·적용 이력을 수정하거나 미적용 migration을 완료로 표시하는 방식은 제외한다. 별도의 정식 마이그레이션 경로 설계와 독립 검토가 필요하며, 이 설계가 확정되기 전에는 예외 실행을 구현하지 않는다. |

| 백업 | 쓰기가 중지된 동일 시점의 DB와 Garage 원본 내용을 복구 가능한 별도 보관 위치에 보존한다. 운영 객체 키를 덮어쓰지 않으며 백업 경로·checksum·용량·접근 권한을 기록한다. |

## 실행 순서와 중단 조건

1. 읽기 전용으로 현재 API·워커 이미지, DB 이력, 관측 기록, 삭제 대기열, Garage 원본 목록과 Pages 설정을 확보한다. 현재 운영 기록과 일치하지 않는 과거 자료는 배포 근거로 사용하지 않는다.
2. 원본 삭제 보류와 백업 복원 검증을 구현하고, 관측 예외의 정식 DB 경로를 확정한다. PR에서 실패 경로까지 검토하고 master에 병합한다.
3. 병합 커밋의 새 불변 이미지를 검증한다. 예외 기록에 정확한 소스·digest와 복구용 이전 소스·digest를 고정한다.
4. 유지보수 전에 저장 용량·Pages 제어·아티팩트·원본 보존 제어를 검사한다. 미확인 항목이 있으면 서비스 중지 전에 종료한다.
5. 기존 CD의 쓰기 중지 절차를 수행한 뒤 DB dump와 Garage 파일 내용 백업을 생성한다. 별도 환경에 DB를 복원하고 파일 크기·checksum·참조 대조를 검증한다. 실패하면 contract를 실행하지 않는다.
6. 자산 대조 및 DB 호환성 검사 후 정확한 master web을 게시하고 contract·승인 요청 migration을 적용한다. 관측 예외와 나머지 검사 결과를 별도로 기록한다.
7. API·워커를 시작하고 인증된 조회·수정·삭제 요청 승인, 원본 및 게시 파일 다운로드를 검증한다. 삭제 기능 검증에는 격리된 시험 데이터를 사용한다. 종료 후 실제 운영 소스·digest와 원본 보존 결과를 기록한다.

## 복구 절차

- contract 이전 실패: DB 적용 이력과 현재 schema를 확인한다. web이 이미 변경된 경우 이전 web과 Phase 1 runtime의 호환성을 함께 복구한다. 원본·백업을 보존하고, 상태를 확인하지 않은 자동 재시작은 수행하지 않는다.
- contract 실행 실패: 트랜잭션과 Prisma 적용 이력을 조회하여 실제 적용 상태를 판정한다. 실패 로그만으로 미적용을 단정하지 않는다.
- contract 이후 실패: 삭제 보류를 유지하고 master 기반 수정 이미지로 전진 복구한다. 이전 이미지 단독 재시작은 금지한다.
- DB 복원이 필요한 경우: 쓰기를 다시 중지하고 실패 시점 DB도 별도로 보존한다. 검증된 backup을 별도 DB에 먼저 복원한 뒤 Garage 원본·참조를 대조한다. 실제 운영 복원은 대상·복원 시점·전환 후 쓰기 처리 범위를 확정한 뒤 수행한다. 이번 문서 작성 동의는 운영 DB 덮어쓰기 승인이 아니다.

## 검증 기준과 미확인 항목

구현 검증에는 기본 관측 경로 유지, 명시적 예외만 허용, 다른 단계의 예외 거부, 잘못된 소스·digest 거부, non-observation 정합성 오류 차단, 재시작 후 원본 삭제 보류 유지, backup·복원 실패 시 DDL 미실행을 포함한다. SQL 실패의 원자성과 전체 마이그레이션 이력 일관성도 실제 PostgreSQL에서 검사한다.

운영 서버 접근 방법, 최신 관측 기록, DB 복원 시험, Garage 파일 내용 백업 및 Pages 권한은 미확인이다. `PAGES_DEPLOY_ACTOR`는 최근 저장소·production 변수 조회에서 없었다. 이 항목들은 관측 조건 생략으로 면제되지 않는다.

현재 구조에서는 관측 예외를 적용한 안전한 배포를 즉시 실행할 수 없다. 우선 원본 보존·복원 검증을 준비하고, 관측 예외가 필요한 시점에도 정상 관측 경로가 충족되지 않는 경우 정식 DB 경로 변경을 별도 검토한다.
