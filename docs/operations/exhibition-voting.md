# 전시회 투표·추첨 운영

## 구현 범위

운영 화면은 `/admin/votes`, 참가자 화면은 `/votes/:publicId`, 공개 기록은 `/votes/:publicId/records`, 추첨·수령 화면은 `/votes/:publicId/draw`이다. `ADMIN`과 `OPERATOR`가 투표·후보·추첨 행사·의심 표시를 관리한다. 투표 주소의 UUID는 개설 시 생성하며 변경·마감·재개 이후에도 유지한다. 영구 삭제 기능은 제공하지 않는다.

운영자는 전시회의 공개 작품을 후보로 가져오거나 투표 전용 포스터를 직접 업로드한다. 전용 업로드는 기존 전시회 소유의 직접 업로드 제어와 이미지 worker를 사용하되 `vote_id`로 용도를 구분한다. 전시회 대표 포스터는 변경하지 않는다. 업로드 session과 output intent를 재사용하여 중단·재시작을 처리한다. 처리 완료 이후에도 미등록 포스터를 운영 화면에서 다시 선택할 수 있다.

공개 작품에서 가져온 포스터는 불변 `DISPLAY_960` 객체에 별도의 `vote_posters` 참조를 생성한다. 복사본 생성 없이 동일한 불변 객체를 보존한다. 원본 조회 전에 객체 삭제 잠금을 획득하며, 참조 목록에 투표 포스터를 포함한다. 원본 작품·자산 삭제 이후에도 투표용 파일 접근을 허용한다. 비공개 작품이나 처리 중인 이미지는 자동으로 후보에 등록하지 않는다. 별도로 업로드한 투표용 이미지는 운영자가 공개 대상으로 지정한 이미지이다.

후보 변경은 투표 버전과 후보 버전을 증가시키며 사유·변경 시각·포스터 참조를 기록한다. 후보 변경 사유는 마감 후 공개된다. 조사 메모는 별도 운영 기록으로 보존한다. 제외 후보의 기존 선택과 득표는 유지한다. 접수 원장에는 제출 당시 작품명·포스터·후보 버전을 저장한다.

## 식별과 원장

참여 식별자는 Web 출처의 `pcu_vote_participant` 쿠키에 저장하는 256비트 난수이다. Web Locks로 여러 탭의 최초 생성을 직렬화한다. 쿠키를 저장할 수 없거나 최초 생성에 필요한 Web Locks를 사용할 수 없으면 참여를 차단하고 안내한다. 다른 브라우저·기기·쿠키 삭제에 따른 재참여를 방지하는 개인 인증 수단은 아니다.

API에는 `X-Vote-Participant` 헤더로 전달하며 DB에는 SHA-256 해시만 저장한다. 토큰은 URL·QR·공개 응답에 포함하지 않으며 API logger의 헤더 마스킹 대상이다. 기존 Origin 검사와 IP 제한을 유지하고 참여자 해시별 분당 120회 제한을 추가한다. 제한 카운터는 프로세스별이며 원장 중복 방지는 DB 고유 제약으로 보장한다.

접수·선택·접수 이력을 한 transaction에서 저장한다. 투표별 참여자, 행사별 참여자, 당첨별 수령 기록에 고유 제약을 적용한다. 기존 결과 조회를 운영 상태 검사보다 먼저 수행하므로 성공 후 응답 유실과 마감 후 재전송에서도 동일한 결과를 반환한다.

## 시간과 추첨

예약 판단은 잠금 획득 이후 PostgreSQL `clock_timestamp()`를 기준으로 수행한다. 준비 상태의 예약 시작, 예약 마감과 30분 유예는 별도 예약 실행 프로세스에 의존하지 않는다. 수동 마감 시에는 마감 시각을 저장한다. 재개 시 과거의 예약 마감을 제거하거나 연장한다.

일시 정지는 해당 투표의 신규 접수와 추첨 자격을 차단한다. 같은 행사에 연결된 다른 유효 투표 참여가 있으면 추첨할 수 있다. 마감 후 유예는 마감 시각부터 30분이며 만료 시각 자체부터 신규 추첨을 차단한다. 이미 확정된 추첨 결과와 수령은 만료 이후에도 조회·처리한다.

유한 추첨함은 활성 항목의 남은 수량, 가중치 추첨함은 활성·미소진 항목의 가중치로 계산한다. 무제한 항목은 가중치 방식에서 사용한다. `crypto.randomInt`로 결과를 결정하고 재고 차감·결과 기록을 한 transaction에서 확정한다. 소진 시 원장을 생성하지 않으므로 재입고 이후 자격 기한 안에서 재시도할 수 있다.

운영자 재고 변경도 동일한 DB 잠금을 사용한다. 추첨 시 설정 버전을 증가시키므로 이전 화면의 수량으로 재고를 덮어쓰려는 운영 요청은 충돌로 거부한다. 결과 항목은 삭제 대신 비활성화하며 설정 스냅샷·재고 변경·각 결과의 계산 근거를 내부에 보존한다. 실행 이후 방식 변경은 기존 상태와 저장할 상태가 모두 일시 정지인 경우에 허용한다.

현재 구현은 투표 기능 전체에 하나의 transaction advisory lock을 사용한다. 여러 API 프로세스의 결과 정합성을 우선한 구성이다. 대규모 동시 접수의 처리량은 별도 부하 측정 대상이며, 잠금 세분화 시 공유 행사와 공개 기록 재차단의 원자성을 유지해야 한다.

## 조사 정보와 수령

조사 정보 수집은 기본적으로 비활성이다. 수집 근거와 참가자 안내를 확정한 뒤 다음 두 환경 변수를 함께 설정한다.

- `VOTE_INVESTIGATION_SECRET`: 로그인 비밀키와 분리한 32자 이상의 난수 비밀키
- `VOTE_PRIVACY_NOTICE`: 목적·항목·30일 보존 기간 등을 포함하여 승인한 참가자 안내

비밀키만 설정하면 API 환경 설정 검증이 실패한다. 안내는 투표 화면의 개인정보 처리 안내에서 제공한다. 수집 항목은 IP의 HMAC-SHA256, 브라우저·OS 계열, 모바일 여부이다. 원문 User-Agent와 원문 IP를 투표 조사 테이블에 저장하지 않는다. API 시작 및 분 단위 maintenance에서 만료 정보를 삭제하며, 운영 조회 전에도 만료 자료를 삭제한다. API 중단 기간에 만료된 자료는 재시작 후 삭제한다. 원장·선택·운영 이력·의심 표시·메모는 이 삭제 대상에 포함하지 않는다.

수령은 참가자 휴대폰의 확인 절차로 처리한다. 직원은 서버 응답으로 표시된 경품·수령 시각·식별번호를 확인한 뒤 지급한다. 수령 시 재고를 다시 차감하지 않는다. 직원 인증이 없으므로 참가자의 선행 클릭이나 위조 화면을 기술적으로 방지하는 절차는 아니다.

## Migration과 출시

`20261008000000_exhibition_voting`은 새 기능 테이블과 nullable `asset_upload_sessions.vote_id`를 추가한다. 기존 행은 변경하지 않는다. 명시적 `BEGIN`·`COMMIT`으로 전체 DDL을 원자적으로 적용한다. 새 제약이 적용되는 기존 upload 행의 `vote_id`는 모두 null이므로 기존 데이터와 충돌하지 않는다. 외부 객체 I/O는 migration에 포함하지 않는다. `20261008010000_vote_poster_ownership`은 포스터의 nullable 투표 소유 관계와 조회 index를 추가한다. 두 migration을 첫 기능 출시 전에 모두 적용한다.

작업 브랜치는 `feat/exhibition-voting`, 기준 source는 `f1e4674`이다. 기존 작업 폴더의 미커밋 변경은 별도 worktree와 분리하여 보존한다. 출시에는 [배포 절차](deployment.md)의 reviewed PR·필수 CI·master 병합·동일 source의 불변 이미지 검증·운영 smoke가 필요하다. Migration 시도 이후 이전 binary/Web의 자동 복구는 수행하지 않는다.

## 검증 기록

로컬 전체 단위·컴포넌트 테스트, lint, architecture 검사, production build가 통과하였다. 전체 17개 통합 suite와 실제 PostgreSQL·Garage·이미지 worker·파일 gateway를 사용하는 smoke도 통과하였다. 전용 포스터 업로드부터 투표·추첨·수령까지 실제 HTTP 경계를 검증하였다. 운영 배포는 수행하지 않았다.

- 실제 PostgreSQL migration chain과 Fastify 인증·serializer를 사용한 투표 통합 suite를 추가하였다. 중복 접수, 후보 변경, 마감·재개·공개 재차단, 공유 행사, 마지막 재고, 재입고, 재고 설정 충돌, 유한·무제한 꽝, 수령 중복, 30일 삭제, 비공개 원본 거부, 원본 삭제 후 파일 접근을 검증한다.
- 실제 HTTP 응답 직전 연결을 종료하여 투표·추첨·수령의 commit 이후 응답 유실과 재시도를 검증한다.
- 별도 이미지 worker repository로 준비된 output의 완료를 재개하고, 전시회 포인터 불변·투표 전용 참조·stale lease 거부·source cleanup 기록을 검증한다.
- 신규 migration의 마지막 단계에 PostgreSQL 오류를 주입하여 신규 테이블·추가 column의 미잔존과 기존 upload 행 보존을 확인하였다.
- Web 테스트는 탭 초기 식별 동시 호출, 저장 불가 안내, 선택 상한, 후보 순서 유지, 최종 확인, 재접속, stale 화면 갱신, 추첨·수령 재조회와 공개 기록 재차단을 확인한다.
- 모바일 Chromium 390×844에서 첫 4장의 2열 배치, 선택 상한, 두 탭의 동일 식별자, 제출 후 양쪽 탭과 새로고침의 완료 화면을 확인하였다. 카드 높이는 약 262px이고 네 번째 카드의 하단은 약 642px이었다.
- Safari용 WebKit 실행은 로컬 시스템 라이브러리 부족으로 완료하지 못하였다. 실제 iOS Safari·Android의 카메라 QR 진입, 장기간 쿠키 보존, 보조기기 조작과 행사장 부하 측정은 운영 전 검증 항목이다.

전용 suite 명령은 `npm run test:integration:suite -- voting`이다. 전체 통합 실행은 기본 Web 포트 5173을 사용한다. 기존 개발 서버가 있으면 `INTEGRATION_WEB_PORT=5180 INTEGRATION_WEB_BASE_URL=http://localhost:5180 INTEGRATION_ORIGIN=http://localhost:5173 npm run test:integration`으로 테스트 Web 포트만 변경한다.
